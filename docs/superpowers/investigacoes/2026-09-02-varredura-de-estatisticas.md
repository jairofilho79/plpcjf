# Investigation: `/offline` forced stats recalculation freeze

Scope: read-only. All line numbers verified against the working tree at HEAD (`1ed4609`) on `main`.

## Real category sizes (measured from `louvores-manifest.json`, 4629 rows)

| raw `categoria` | count | normalizes to |
|---|---|---|
| Partitura | 1654 | Partitura |
| Cifra nível I | 1036 | Cifra |
| Cifra nível II | 1033 | Cifra |
| Cifra | 652 | Cifra |
| Gestos em Gravura | 254 | Gestos em Gravura |

`CATEGORY_OPTIONS` (`src/lib/stores/filters.js:6`) is only 3 entries (`Partitura`, `Cifra`, `Gestos em Gravura`) — the "5 categories" the user counted are the 5 raw `categoria` strings above; `loadCategoryStats` (`src/routes/offline/+page.svelte:733`) only calls `getCategoryStats` 3 times, once per normalized bucket, with `_getCategoryVariants` (`StatsCalculator.js:315-320`) folding the 3 Cifra variants together (2721 louvores) inside a single call.

All three normalized buckets exceed the `>100` chunking threshold at `StatsCalculator.js:149`, so **all three** go through the chunked path, not just the big ones.

## A. The cost model

One full forced recalculation (`loadCategoryStats(true)` → `loadCategoryStatsForCategories(CATEGORY_OPTIONS, true)`) does one Cache-Storage read of the whole PDF cache up front, then re-derives the same lookup structure from that one read **95 separate times** while walking the catalogue in 50-item slices. The Cache Storage layer itself is touched once (maybe twice); the cost is JS-side re-hashing of a list of already-fetched URLs, done far more often than the one time it's actually needed.

| Operation | Count for the full run | Where |
|---|---|---|
| Full catalogue array scans (`.filter` over all 4629 louvores) | 3 (one per normalized category) | `StatsCalculator.js:138` |
| Chunk iterations (50 louvores each) | 34 (Partitura) + 55 (Cifra) + 6 (Gestos) = **95** | `StatsCalculator.js:153-159` |
| `findMissingPdfs()` calls | 95 (+1 more if `selectedCategories.length>0` triggers `getRequiredPackagesInfo`) | `StatsCalculator.js:155`, `pdfValidation.js:269` |
| `buildPdfCacheIndex()` rebuilds — each one re-walks and re-normalizes the **entire** cached-PDF list (size `C`, ≤4629, unknown exact value — see caveat below) | **95**, should be **1** | `pdfValidation.js:286` |
| Cache-index entries normalized (`PdfPathManager.normalizeForStorage`, incl. `.normalize('NFC')`) inside those rebuilds | 95 × `C` (≈ 4.4×10⁵ if `C`≈4629) | `pdfCacheIndex.js:63-68`, `PdfPathManager.js:26-70` |
| `cacheIndex.has()` lookups (one per louvor, each redoing `toComparablePath` + NFC normalize on the query side) | ~4629 (once per louvor with a `pdfId`, not repeated) | `pdfValidation.js:296`, `pdfCacheIndex.js:72-77` |
| `atobUTF8` base64 decodes of `pdfId` | ≤4629, and **only once ever** per unique `pdfId` (memoized) | `pathUtils.js:39-73` (`pdfRelPathCache`) |
| Real Cache Storage calls (`cache.keys()`/`cache.match()`) | **1**, occasionally 2 (retry-if-empty) — done inside the Service Worker, not in a per-louvor loop | `service-worker.js:504-521`, `swRegistration.js:356-401` |
| localStorage stats-cache read/write (`cacheStats`) | 3 (one JSON parse+stringify per category, small payload) | `statsCache.js:260-...` |

The dominant, avoidable cost is the 95× rebuild of `buildPdfCacheIndex`. Everything that touches actual Cache Storage happens O(1) per run, not O(louvores) — the freeze is CPU work on strings/URLs, not async I/O.

## B. Hot spots, ranked

**1. `buildPdfCacheIndex` rebuilt once per 50-item chunk instead of once per run** — `pdfValidation.js:286` (called from `StatsCalculator.js:155` and `:164`)
Every call to `findMissingPdfs(chunk, cachedPdfsList)` reconstructs the whole `Set` of normalized cached paths from `cachedPdfsList` from scratch, even though `cachedPdfsList` is the exact same array object across all 95 chunks and all 3 categories (`StatsCalculator.js:124` receives it once from the caller and never mutates it). This is the only step whose cost scales with the size of the *entire* cache (`C`), and it pays that cost 95 times instead of once. This is far and away the biggest lever: cutting it to 1 build removes ~99% of the `buildPdfCacheIndex` work.

**2. Per-entry Unicode/URL normalization inside that rebuild** — `pdfCacheIndex.js:63-68` calling `PdfPathManager.normalizeForStorage` (`PdfPathManager.js:26-70`, which runs 2 regex replaces, an optional `decodeUrlUtf8Multiple` loop, `.normalize('NFC')`, `.toLowerCase()`, and 2 more replaces) plus `toComparablePath` (`pdfCacheIndex.js:25-42`, a `new URL()` construction plus a regex fallback) for every entry of `cachedPdfsList`. This is the actual synchronous hot loop: it's cheap per call (microseconds) but is executed 95×`C` times because of hot spot #1, which is exactly the "per-path Unicode normalization repeated" pattern this project has hit before (see the `#22.2`/`#22.3` comments in `pdfCacheIndex.js` and `PdfPathManager.js` — the normalization itself is *necessary*, it's the repetition that's new damage). This is the synchronous work that blocks the main thread long enough to starve the `setTimeout(resolve, 0)` yields between chunks (`StatsCalculator.js:159-161`) and the DevTools CDP pump.

**3. `cacheIndex.has()` throws-and-catches a real exception on every louvor lookup** — `pdfCacheIndex.js:72-77` → `toComparablePath` (`:25-42`). The candidate passed in is `getPdfRelPath(louvor)` (`StatsCalculator.js` via `pdfValidation.js:293`), a **relative** path like `assets/…/Cifra.pdf`. `new URL(candidate)` (`pdfCacheIndex.js:29`) always throws for a relative string with no base — the code relies on the `catch` to fall through to the regex fallback (`:31-34`), which also fails to match and leaves `pathname` as the original string. So every one of the ~4629 `has()` calls pays for a genuine thrown-and-caught `TypeError`, on the hot path, by design rather than by accident. This is smaller than #1/#2 in raw operation count but exceptions are one of the few JS constructs with real fixed overhead beyond the work they wrap, and it happens on literally every louvor.

**4. Repeated `getCachedPDFsFast()`/`loadCachedPdfsList()` invalidation cascade** — `src/lib/stores/offline.js:324-374`. Every call to `loadCachedPdfsList` (called at `+page.svelte:583`, and again in the empty-retry branch at `:596`) unconditionally calls `statsCalculator.invalidateAll()` (`offline.js:331-332`) and `clearAllValidationCache()` (`offline.js:367`), regardless of whether anything actually changed. This isn't O(louvores) by itself, but it means a single forced recalculation can trigger the invalidate-everything path twice before any category math even starts, and every other place in `+page.svelte` that calls `loadCachedPdfsList` (10 call sites) pays the same tax. It's a correctness-safe but wasteful default that compounds with #1 if any caller re-enters the stats flow while a forced recalculation is still resolving.

**5. `_cacheResult` / `cacheStats` full-blob read-modify-write per category** — `StatsCalculator.js:340-361` → `statsCache.js:260-...`. Each of the 3 categories does one `localStorage.getItem` + `JSON.parse` + mutate + `JSON.stringify` + `setItem` of the *entire* stats blob (all categories), not just its own entry. With only 3-5 categories this is currently negligible (small payload), but it's a full parse/stringify pass done synchronously 3 times per run and would degrade if the cached-stats payload grows (e.g. if per-category `missing` PDF lists were ever added to the cache). Ranked last because today it costs microseconds, not the seconds/minutes the freeze is about.

## C. Concrete fixes

**Fix for #1 (the big one) — hoist `buildPdfCacheIndex` out of `findMissingPdfs` and out of the per-category call.**
- Change `findMissingPdfs(louvores, cachedPdfs)` in `pdfValidation.js:269` to accept an already-built index: `findMissingPdfs(louvores, cachedPdfsOrIndex)`, detecting via a small helper (`isPdfCacheIndex(x)` — check for `.has`/`.size`) whether the second argument is a raw array (build once, as today, for backward compatibility with the other 3 call sites: `offlineStats.js:16`, `missingPdfsDownloader.js:87`, `DownloadManager.js:172`) or a pre-built index (skip rebuilding).
- In `StatsCalculator.getCategoryStats` (`StatsCalculator.js:49`), build the index **once** right after `cachedPdfsList` is resolved (around line 134, before the `_normalizeCategory` block at line 135), and pass that index into every chunk's `findMissingPdfs` call instead of `cachedPdfsList` itself (lines 155 and 164).
- Better still: build the index once in `loadCategoryStatsForCategories` (`+page.svelte`, right after `cachedPdfs` is resolved around line 590) and pass it through `options.cachedPdfs` to all 3 (soon-to-be-parallel) `getCategoryStats` calls, since today's `cachedPdfsList` is already shared across categories — this removes the "expensive work repeated per category" the task asked about explicitly.
- **Trade-off / behavior change:** none in output — same missing/available numbers, since `buildPdfCacheIndex` is a pure function of `cachedPdfsList` regardless of how many times it runs. This is a pure win: 95 rebuilds → 1. It does mean `StatsOptions.cachedPdfs` implicitly gains a second accepted shape (array or index); document it in the JSDoc typedef at `StatsCalculator.js:24-29`.

**Fix for #2 — cache the normalized form of each cached URL alongside the raw list, and avoid renormalizing per lookup.**
- Since #1 already collapses the 95× repetition down to 1 build, the remaining per-entry normalize cost is now unavoidable *if* `cachedPdfsList` changes between runs. To avoid recomputation even across separate forced recalculations (e.g. user clicks "recalculate" twice in a row without any download happening in between), memoize the built index keyed by identity or a cheap fingerprint of `cachedPdfsList` (e.g. its `.length` plus first/last URL, or a version counter bumped only in `loadCachedPdfsList`) inside `StatsCalculator` (a new `this._cacheIndexCache` field, invalidated in `invalidateAll()`).
- **Trade-off:** introduces one more piece of invalidation-sensitive state; must be cleared whenever `cachedPdfsList` actually changes (downloads, imports, cache clears) or stats will report stale availability. Given `loadCachedPdfsList` already calls `statsCalculator.invalidateAll()` on every refresh (hot spot #4), wiring the index cache to clear there is low-risk and consistent with existing semantics.

**Fix for #3 — skip the `new URL()` throw for relative candidates.**
- In `toComparablePath` (`pdfCacheIndex.js:25-42`), check cheaply whether `url` already looks absolute (`/^[a-z]+:\/\//i.test(url)` or simply `url.includes('://')`) before attempting `new URL(url)`, and only construct the URL object in the branch that needs it. For the `has()` side (candidate = relative `pdfPath`), this skips straight to treating the string as a pathname with no attempted construction, removing ~4629 thrown exceptions per run.
- **Trade-off:** none observable — same result, since the exception path today falls through to using the original string anyway when both the URL constructor and the regex fail to change it meaningfully for a relative path. Purely a speed fix.

**Fix for #4 — make `loadCachedPdfsList`'s invalidation conditional on the PDF list actually changing.**
- In `offline.js:324-374`, compare the newly fetched `cachedUrls.length` (and ideally a cheap hash, e.g. length + last-modified-ish marker) against the previous value in `offlineState` before calling `statsCalculator.invalidateAll()` / `clearAllValidationCache()`. Only invalidate when the count (or a real diff) changed.
- **Trade-off:** this changes staleness semantics — a same-length-but-different-content cache swap (rare: would require removing and adding the same number of different PDFs between two calls with no other invalidation in between) would be missed. Given every actual mutation path (download completion, ZIP import, cache clear) already calls explicit `invalidateCategory`/`invalidateCategories` at the point of mutation (`+page.svelte:356,481,517,773`), this is a low-risk tightening, but it should be called out to reviewers as a staleness-semantics change, not a pure no-op optimization.

**Fix for #5 — not urgent.** If the stats cache payload ever grows (e.g., someone adds per-category missing-PDF-id lists to it), switch `cacheStats`/`getCachedStats` (`statsCache.js`) to store one `localStorage` key per category instead of one shared blob, avoiding the full-payload parse/stringify per category. Not worth doing before #1–#3 land; today's payload is a few hundred bytes.

## Answers to the numbered questions

1. **Algorithmic shape, one category:** the catalogue is traversed once via `.filter` (`StatsCalculator.js:138`) to select the category's louvores, then that subset is walked once more in 50-item chunks (`:153`). Per chunk, `findMissingPdfs` rebuilds a `Set` over the *entire* cached-PDF list (`pdfValidation.js:286`) — so the real shape for one category is **O(louvores_in_category) traversal + O(chunks_in_category × C) for the repeated index rebuilds**, where `C` = size of `cachedPdfsList`. Across all 3 categories, with `C` roughly constant, total work is **O(catalogue) + O(95 × C)** — dominated by the second term whenever `C` is not tiny. Real Cache Storage operations are O(1) per run, not part of this scaling.

2. **Expensive work repeated per category that could be done once for all:** yes — `buildPdfCacheIndex(cachedPdfsList, …)` (`pdfValidation.js:286`). `cachedPdfsList` is identical across all 3 category calls (passed straight through from `loadCategoryStatsForCategories`, `+page.svelte:590` → `StatsCalculator.js:640-647`), so the index built from it should be computed once for the whole run, not once per chunk per category.

3. **Is `cache.keys()`/`cache.match()` called inside a loop?** No — for this flow they are not. `cache.keys()` runs exactly once inside the Service Worker per `getCachedPDFsFast()` call (`service-worker.js:506-507`), and `getCachedPDFsFast()` itself is called once (occasionally twice, via the empty-retry branch at `+page.svelte:593-599`) for the whole forced recalculation, not per category or per louvor. `CacheStorageAdapter.js`'s `cache.match`/`cache.keys` (lines 169, 199, 513, 626) are not on this code path at all — `StatsCalculator` imports `cacheStorageAdapter` (`StatsCalculator.js:9,38`) but never calls any method on it; it's dead weight in this class. The freeze is not Cache Storage I/O — it's the 95× synchronous JS rebuild described above.

4. **What blocks the main thread:** the synchronous hot spot is `buildPdfCacheIndex`'s per-entry loop (`pdfCacheIndex.js:63-68`) calling `PdfPathManager.normalizeForStorage` (`PdfPathManager.js:26-70`: regex replaces + `decodeUrlUtf8Multiple` + `.normalize('NFC')` + `.toLowerCase()`) and `toComparablePath` (`new URL()` + regex), executed 95 times over the full cached-PDF list instead of once. Secondarily, `cacheIndex.has()` (`pdfCacheIndex.js:72-77`) throws and catches a `TypeError` from `new URL()` on every one of the ~4629 louvor lookups. Neither `atobUTF8` (memoized, `pathUtils.js:39-95`) nor a `.map`/`.filter`/`.find` chain over the full catalogue is the culprit — those parts of the code are already cheap or already memoized; it's specifically the *rebuild count* of the cache index that turns an O(C) operation into an O(95×C) one.

5. **What's memoized/indexed already, and why it doesn't help here:**
   - `pdfRelPathCache` (`pathUtils.js:83-95`) memoizes `getPdfRelPath(louvor)` (base64 decode + path decode) per `pdfId`, forever, across categories and across forced recalculations. This *does* help — it's why base64 decoding isn't a hot spot despite running once per louvor.
   - `statsCache.js` (localStorage, `STATS_CACHE_KEY`) and `StatsCalculator.memoryCache` (`StatsCalculator.js:38`) memoize the **final per-category result** (`{total, available, missing, percentage}`), keyed by category, with a 24h TTL (persistent) / 60s TTL (memory). `forceRecalculate: true` (set by every call in this flow, `+page.svelte:646`) explicitly skips both checks (`StatsCalculator.js:60,71`), so on a forced run neither cache is ever consulted — by design, since the whole point of the "recalculate" button is to bypass stale results. This is correct behavior, but it means **nothing** memoized today covers the *intermediate* cache-index structure, only the final numbers — so a forced run gets zero benefit from either cache and pays the full (and inflated, per hot spot #1) cost every time.
   - `pdfCacheIndex.js`'s index itself is not memoized anywhere — it's rebuilt fresh on every `findMissingPdfs` call and thrown away immediately after. There is no module-level or instance-level cache for it today; that's precisely the gap the Fix for #1/#2 above closes.

6. **Redundant normalization per louvor per category?** Not per *category* — each louvor belongs to exactly one normalized category (the 3 Cifra variants collapse into one category, but a given louvor is still only visited once), so there's no cross-category duplication of `getPdfRelPath`/`atobUTF8` work. The redundant normalization is per **chunk**, on the *cached-PDF side*: the same `cachedPdfsList` entries get normalized 95 times over (once per chunk) instead of once, which is the project's known "path normalization repeated" failure mode recurring in a new spot (previous fixes, per the `#22.x` comments in `pdfCacheIndex.js`/`PdfPathManager.js`, addressed correctness of normalization; this is a new performance instance of the same operation being called far more than necessary).

## Bugs flagged (not just slowness)

- **`pdfCacheIndex.js:29`** — `toComparablePath` calls `new URL(candidate)` on values that are routinely relative paths (from `getPdfRelPath`), guaranteeing a thrown `TypeError` on the majority of `has()` calls. It happens to be caught and handled correctly (functionally harmless), but it is an exception used for control flow on a hot path, which is worth fixing regardless of the raw speed gain (see Fix #3).
- **`StatsCalculator.js:9,38`** — `cacheStorageAdapter` is imported and assigned to `this.cacheAdapter` but never called anywhere in the class. Either dead code that should be removed, or a sign that a planned direct-Cache-Storage read path was never wired in (worth confirming with git history/blame before deleting, but as it stands it does nothing).
- **`offline.js:331-332` / `:367`** (inside `loadCachedPdfsList`) — unconditionally invalidates all stats and all PDF-validation cache entries on *every* call, including calls that don't originate from an explicit "recalculate" action (e.g. `+page.svelte:1039,1107,1170,1302`). Not incorrect, but it means routine cache-list refreshes silently force full recalculation elsewhere in the app; flagged under Fix #4 as a staleness/perf trade, not purely a bug.

## What I could not determine from the code alone

- **The exact value of `C`** (how many PDFs are actually sitting in Cache Storage during the observed 2m30s run) — this is the single biggest unknown feeding the cost model's magnitude. The counts and shape (95 rebuilds instead of 1) are certain from the code; the actual wall-clock impact of "95×" depends on `C`, which is a runtime fact, not a code fact. **Measurement that would answer it:** in DevTools Console during a real run, `(await caches.open('<PDF_CACHE_NAME>')).keys().then(k => k.length)` (the cache name constant lives in `src/service-worker.js`, search `PDF_CACHE`), or simply log `cachedPdfsList.length` at `+page.svelte:604` (a `console.log` already exists there guarded by `if (force)` — it already fires on every forced run, so the count should already be visible in the console history from the reported freeze).
- **The per-call cost of `normalizeForStorage`/`toComparablePath` in the actual browser/engine** — I gave microsecond-scale reasoning from the operations involved (regex, `new URL()`, `.normalize('NFC')`), but did not and could not measure it. **Measurement that would answer it:** a Chrome DevTools Performance recording of one forced recalculation, with attention to time spent under `buildPdfCacheIndex` / `normalizeForStorage` in the flame chart — this would also confirm or correct the "95× rebuild is the dominant cost" ranking against, e.g., garbage-collection pressure from 95 freshly-allocated `Set`s of size `C`, which the code alone can't quantify either.
